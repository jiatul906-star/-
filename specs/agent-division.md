# 子代理分工

> 状态：已确认 | 最后更新：2026-07-01
>
> 本文档定义 Codex/Superpower 多子代理协作时的角色、职责、交付接口和 AC 分配。
> 驾驭工程（Harness Engineering）核心原则：**写代码的 ≠ 写测试的 ≠ 验收的。**

---

## 二、五个代理详细定义

### 2.1 架构代理（Architect Agent）

| 属性 | 内容 |
|------|------|
| **一句话职责** | 读完所有相关文档和源码后，给出精确的实现方案（改哪些文件、怎么改、注意事项） |
| **输入** | AC 编号 + `specs/requirements.md` 相关章节 |
| **必读文件** | `ag.md` → `CLAUDE.md` → `docs/architecture.md` → `docs/interfaces.md` → `docs/design-system.md` → 涉及 AC 的对应源码 |
| **输出** | 实现方案（Markdown），必须包含：① 要修改的文件清单（完整路径）② 每个文件的修改要点 ③ 新增 IPC 通道（如有）④ 风险点/注意事项 ⑤ 依赖顺序（先改 A 再改 B） |
| **不做什么** | 不写代码、不运行应用、不修改文件 |
| **完成标志** | 方案被用户或 Coder Agent 确认可执行 |

**输出模板**：

```markdown
# 实现方案：AC-X.Y 功能名称

## 涉及文件

| 文件 | 操作 | 说明 |
|------|------|------|
| `src/renderer/components/Foo.tsx` | 修改 | 在第 N 行附近添加 XXX 逻辑 |
| `src/main/ipc/index.ts` | 新增 handler | 新增 `foo:bar` IPC 通道 |

## 修改要点

### 1. `src/renderer/components/Foo.tsx`
- 在 `handleClick` 中添加 XXX
- 新增 `useEffect` 监听 YYY
- ⚠️ 注意：必须走 persist 三步

### 2. `src/main/ipc/index.ts`
- 新增 `ipcMain.handle('foo:bar', ...)` 
- 数据存储在 `%APPDATA%/ai-companion/foo.json`

## 新增 IPC 通道（如有）
| 通道名 | 方向 | 载荷 |
|--------|------|------|
| `foo:bar` | renderer→main | `{ id: string }` |

## 风险
- XXX 可能影响 YYY，需回归测试 AC-Z.Z

## 依赖顺序
1. 先改 `src/common/types.ts` 添加类型
2. 再改 `src/main/ipc/index.ts` 注册 IPC
3. 再改 `src/preload/index.ts` 暴露 API
4. 最后改组件
```

### 2.2 编码代理（Coder Agent）

| 属性 | 内容 |
|------|------|
| **一句话职责** | 按实现方案写代码，遵守 CLAUDE.md 全部约束，写完后自述改了什么 |
| **输入** | Architect Agent 的实现方案 + AC 原文 |
| **必读文件** | 方案中列出的所有文件 + `CLAUDE.md` 五大约束 |
| **输出** | 变更清单（Markdown）：每个修改文件的 diff 摘要 + 新增文件列表 |
| **不做什么** | 不运行应用、不截图、不验收、不修改 ASAR 产物 |
| **完成标志** | `npx electron-vite build` 无 TypeScript 错误 |

**强制约束**（来自 `CLAUDE.md`）：
1. `src/` 是唯一真相源，不允许只修改 ASAR
2. 不允许硬编码 UI 值，全部从 CSS 变量读取
3. 所有表单输入必须 value/onChange 绑定 + 持久化
4. 外部依赖方案必须零用户门槛
5. 模块间通信只走已定义的 IPC 通道（见 `docs/interfaces.md`）

---

### 2.3 测试编写代理（Test Writer Agent）

| 属性 | 内容 |
|------|------|
| **一句话职责** | 根据 AC 的量化标准和失败判定，写出逐步骤的验证脚本（不是代码测试，是人工/AI 可执行的验证步骤） |
| **输入** | AC 原文 + Coder Agent 的变更清单 |
| **输出** | 验证脚本（Markdown），包含：① 前置条件 ② 逐步骤操作 ③ 每步预期结果 ④ 截图/录屏清单（每步要截什么） |
| **不做什么** | 不写单元测试代码、不运行应用、不截图 |
| **完成标志** | 验证脚本覆盖了 AC 的所有量化标准和失败判定 |

**验证脚本模板**：

```markdown
# 验证脚本：AC-X.Y 功能名称

## 前置条件
- [ ] `npx electron-vite build` 成功
- [ ] 删除 `%APPDATA%/ai-companion/` 下的旧数据（如需要）
- [ ] 启动应用：`npx electron .`

## 验证步骤

### 步骤 1：XXX
- 操作：点击设置按钮
- 预期：设置窗口出现，尺寸 780×560
- 截图/录屏：`AC-X.Y_step1.png`（全窗口截图）

### 步骤 2：YYY
- 操作：输入文字 "测试" → 点击保存
- 预期：输入内容出现在聊天窗口
- 截图/录屏：`AC-X.Y_step2.png`

## 证据清单
| 文件 | 步骤 | 内容 |
|------|------|------|
| `AC-X.Y_step1.png` | 1 | 设置窗口全貌 |
| `AC-X.Y_step2.png` | 2 | 保存后效果 |
```

---

### 2.4 验证代理（Verifier Agent）

| 属性 | 内容 |
|------|------|
| **一句话职责** | 按验证脚本逐步骤执行，截图/录屏，打包证据，自检是否全部通过 |
| **输入** | Test Writer Agent 的验证脚本 |
| **输出** | 证据包：① 所有截图/录屏（按命名规范）② 自检清单（每步 Pass/Fail + 说明） |
| **不做什么** | 不修改代码、不修改验证脚本 |
| **完成标志** | 所有步骤已完成（Pass 或 Fail），证据文件齐全 |

**证据命名规范**：`AC-X.Y_stepN_desc.png` 或 `AC-X.Y_full.mp4`

**禁止行为**：
- ❌ 用 "代码中已实现" 作为证据
- ❌ 用控制台日志代替截图
- ❌ 局部裁切截图（必须全窗口）
- ❌ 跳过失败步骤不报告

---

### 2.5 审查代理（Reviewer Agent）

| 属性 | 内容 |
|------|------|
| **一句话职责** | 对照 AC 原文，审查 Verifier 的证据包，逐项判定 Pass/Fail，输出最终验收报告 |
| **输入** | AC 原文 + Verifier 的证据包 |
| **输出** | 验收报告（Markdown）：① 每条量化标准的判定（✅/❌）② Fail 项的具体原因 ③ 建议修复方案 |
| **不做什么** | 不修改代码、不重新截图 |
| **完成标志** | 验收报告覆盖了 AC 的所有量化标准，无遗漏 |

**判定规则**：
- 证据清晰且符合量化标准 → ✅ Pass
- 证据模糊/不完整 → 🔄 退回 Verifier 补充证据
- 证据明确不符合量化标准 → ❌ Fail（附原因和建议修复方案）
- 无法验证（如需要特殊硬件）→ ⏸️ Blocked（说明阻塞原因）

## 三、典型工作流

### 3.1 单个功能开发流程

```
用户指定 AC-X.Y
    │
    ▼
[Architect Agent] 读文档 → 出实现方案
    │
    ▼ （方案确认）
[Coder Agent] 按方案写代码 → build 通过 → 出变更清单
    │
    ├──→ [Test Writer Agent] 出验证脚本
    │         │
    │         ▼
    │    [Verifier Agent] 启动应用 → 执行 → 截图 → 出证据包
    │         │
    │         ▼
    │    [Reviewer Agent] 对照 AC 审查 → 出验收报告
    │         │
    │         ├── ✅ 全部 Pass → 用户最终确认 → 标记 AC 完成
    │         ├── 🔄 证据不全 → 退回 Verifier
    │         └── ❌ 有 Fail → 退回 Coder（附 Review 报告）
    │
    └── （Coder 收到 ❌ 时）读 Review 报告 → 修复 → 重新 build → 再次交 Test Writer
```

### 3.2 并行流水线（多 AC 同时推进）

```
Architect Agent（AC-3.9）
    │
    ▼
Coder Agent（AC-3.9）
    │
    ├──→ Test Writer（AC-3.9） → Verifier（AC-3.9） → Reviewer（AC-3.9）
    │
    └── （同时）Coder 开始 AC-3.10（如果 AC-3.9 不阻塞 AC-3.10）

Architect Agent（AC-3.10）
    │
    ▼
Coder Agent（AC-3.10）
    │
    └──→ Test Writer（AC-3.10） → Verifier（AC-3.10） → Reviewer（AC-3.10）
```

**并行条件**：两个 AC 不修改同一文件的同一区域，否则必须串行。

## 五、代理间交付接口

### 5.1 交付物规范

| 代理 | 交付物 | 格式 | 存放位置建议 |
|------|--------|------|-------------|
| Architect | 实现方案 | Markdown | `specs/plans/AC-X.Y_plan.md` |
| Coder | 变更清单 | Markdown | `specs/plans/AC-X.Y_changes.md` |
| Test Writer | 验证脚本 | Markdown | `specs/plans/AC-X.Y_test-script.md` |
| Verifier | 证据包 | PNG/MP4 + 自检清单 | `specs/evidence/AC-X.Y/` |
| Reviewer | 验收报告 | Markdown | `specs/evidence/AC-X.Y_verdict.md` |

### 5.2 阻塞与升级

```
Coder 发现方案不可行
  → 退回 Architect（附具体原因："方案说改 Foo.tsx，但该文件不存在/逻辑冲突"）

Verifier 无法执行验证脚本
  → 退回 Test Writer（附具体原因："步骤3需要GPU但当前环境无GPU"）

Reviewer 发现证据不全
  → 退回 Verifier（附缺失清单："缺少步骤2的截图"）

Reviewer 发现 Fail
  → 升级到用户 + 退回 Coder（附 Review 报告）

连续 2 次退回 → 升级到用户决策
```

## 六、禁止的偷懒行为

| ❌ 偷懒行为 | ✅ 正确做法 |
|------------|------------|
| Architect 不读源码就出方案 | 必须 `Read` 所有涉及文件后再写方案 |
| Coder 跳过 build 验证 | 每次修改后必须 `npx electron-vite build` 检查 |
| Test Writer 抄 AC 原文当验证脚本 | 必须结合 Coder 的实际变更写具体操作步骤 |
| Verifier 用旧截图冒名顶替 | 每次验证必须全新截图，文件名含时间戳 |
| Reviewer 只看截图不看 AC | 必须逐条对照 AC 量化标准判定 |
| 任一代理说 "代码已实现" | 这句话在任何代理的输出中禁止出现 |
| Coder 改 IPC 但不更新 preload | 主进程 + preload + 类型定义必须同步更新 |
