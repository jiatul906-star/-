# 架构方案分析

> 状态：方案已确定（C）| 最后更新：2026-05-15

## 背景

AI 聊天工具包含五个功能模块：AI 聊天、DIY 角色创建、TTS 语音、桌宠、多角色管理。需要确定它们之间的组织方式。

## 三种方案

### 方案 A：独立模块 —— 各自独立程序

每个功能是独立小程序，共享一份数据。

```
┌─ 聊天窗口 ─┐    ┌─ 桌宠 ─┐    ┌─ DIY编辑器 ─┐
│   AI对话    │    │  动画   │    │  角色配置    │
│   TTS播放   │    │  交互   │    │  图片上传    │
└─────────────┘    └────────┘    └──────────────┘
       ↕                ↕               ↕
  ┌─────────────────────────────────────────┐
  │              共享数据层                   │
  │         (角色配置、聊天记录)               │
  └─────────────────────────────────────────┘
```

| 优点 | 缺点 |
|------|------|
| 模块独立，一个崩了不影响其他 | 整体感差，用户感觉是"几个软件" |
| 可分别开发、分别更新 | 模块间通信复杂，数据同步易出错 |
| 桌宠可独立悬浮 | 安装包可能是多个，体验割裂 |

### 方案 B：大一统单体 —— 所有功能在一个窗口

```
┌──────────────────────────────┐
│         主窗口                 │
│  ┌─ 标签栏 ─────────────────┐ │
│  │ 聊天 │ DIY │ 设置 │ ...  │ │
│  ├──────────────────────────┤ │
│  │                          │ │
│  │   当前功能区域             │ │
│  │                          │ │
│  ├──────────────────────────┤ │
│  │   底部状态栏（桌宠小窗）    │ │
│  └──────────────────────────┘ │
└──────────────────────────────┘
```

| 优点 | 缺点 |
|------|------|
| 整体感强，体验统一 | 代码耦合，改一处可能影响全局 |
| 开发简单，数据共享容易 | 越来越臃肿，维护成本递增 |
| 一个安装包搞定 | 桌宠局限在窗口内，无法悬浮桌面 |

### 方案 C：壳 + 插件 —— 主程序 + 独立模块插件

轻量主程序（壳），每个功能是插件，可独立窗口也可嵌入。

```
┌──────────────────────┐
│      主程序（壳）      │
│  ┌──────────────────┐│
│  │ 插件系统          ││
│  │ ├ 聊天插件        ││
│  │ ├ DIY插件         ││
│  │ ├ TTS插件         ││
│  │ └ 桌宠插件 ← 可弹出独立窗口 ││
│  └──────────────────┘│
│                      │
│  共享：UI主题/数据/AI │
└──────────────────────┘
```

| 优点 | 缺点 |
|------|------|
| 整体感 + 模块独立性兼得 | 前期搭框架需要时间 |
| 桌宠可弹出桌面，也可嵌在主窗口 | 对架构设计能力有要求 |
| 后续加新功能不伤筋骨 | |

---

## Claude 的推荐：方案 C

理由：

1. **桌宠天生需要独立窗口** — 必须能从主窗口弹出，A 能做到但体验割裂，B 做不到
2. **DIY 是核心竞争力** — 以后大概率有新想法，插件架构加功能不用重写
3. **上次崩盘就是因为架构缺乏约束** — 插件系统本身就是约束，逼着每个模块按规矩来

代价：搭框架多花一周左右。收益：后面加功能成本大幅降低。

## ✅ 决策已确认（2026-05-15）

### 问题 1：插件框架方案 → **简单模块加载**

插件通过 ES module `import()` 动态加载，共享渲染进程。插件间通过壳层事件总线通信。

```
src/
├── core/           # 壳（窗口管理、主题、IPC）
├── plugins/
│   ├── chat/       # import { ChatPlugin } from './plugins/chat'
│   ├── diy/
│   ├── tts/
│   └── pet/
└── shared/         # 公共类型、工具、数据层
```

**理由**：
- 唯一开发者，所有插件可控，无需进程隔离
- 桌宠独立窗口 ≠ 桌宠独立进程 — 可以用独立 BrowserWindow 但代码仍共享加载
- 省掉 IPC 层开发时间，投入在核心功能上

### 问题 2：桌宠桌面悬浮 → **BrowserWindow 透明置顶 + IPC 同步**

桌宠使用独立透明 BrowserWindow（`transparent + alwaysOnTop + frame: false`），与主窗口通过 IPC 同步位置。

```
主窗口（聊天/设置）         桌宠窗口（独立 BrowserWindow）
  move/resize 事件 ──IPC──→   setBounds({ x, y })
  状态变化通知      ←──IPC──   拖拽/交互事件
```

**核心配置**：
- `transparent: true` — 背景透明，只显示角色
- `alwaysOnTop: true` — 桌面悬浮
- `frame: false` — 无边框
- `setIgnoreMouseEvents(true, { forward: true })` — 透明区域穿透，角色本体取消穿透可交互
- `skipTaskbar: true` — 不在任务栏显示

**骑乘态**：主窗口 `move`/`resize` 事件 → IPC 发送坐标 → 桌宠窗口 `setBounds()` 跟随

**自由态**：用户拖拽角色离开窗口 → 停止跟随 → 角色独立悬浮桌面

**过渡动画**：CSS transition 300ms ease-out
